# ADR-002: Build a Custom PSR-11 Container (CORE-02)

**Status:** Accepted
**Date:** 2026-08-04
**Deciders:** DGLab architecture team

## Context

`packages/core/container/composer.json` declares the contract for CORE-02 as: *"PSR-11 compliant Dependency Injection Container with autowiring, compiler passes, and circular dependency detection."* The runtime dependency surface is intentionally minimal: `php: ^8.3` and `psr/container: ^2.0` are the only `require` entries. `psr/log: ^3.0` is `suggest`-only (diagnostic logging during compilation). Finding 8 in `00_CRITIQUE.md` records that `packages/core/container/src/` contains only `.gitkeep` — zero PHP files, zero interfaces, zero tests — yet CORE-02 is the single most-depended-on component in the entire Hub tier. Every Hub blueprint's "Integration Strategy" section assumes `CORE-02` is resolved before its own services can be constructed.

This ADR is required *before* the first line of CORE-02 code is written, because the build-vs-adopt decision is irreversibly expensive. Adopting PHP-DI or Symfony DI today means every downstream Hub blueprint's service provider will inherit that library's API surface; ripping it out later would touch every Hub package simultaneously. Conversely, building a custom container means committing to maintain a reflection layer, a compiler pass system, and a circular-dependency detector for the lifetime of the stack.

Three forces push toward building rather than adopting. First, the Sovereign Stack's stated design principle is "sovereign": the fewer external runtime dependencies, the smaller the supply-chain attack surface and the more control we retain over the dependency injection graph. Second, CORE-02 has explicit performance targets — sub-1ms resolution, sub-0.5ms for 3-level deep dependency trees, sub-1MB container overhead (per `docs/blueprints/Core/CORE-02.md`) — that demand compiler-pass-driven, flat-array-optimized resolution; general-purpose containers optimize for flexibility, not for this specific profile. Third, the container must integrate with the future SuperPHP reactive system (CORE-07/11/12), which will need to inject `@persist`-scoped services in ways that none of the off-the-shelf containers model cleanly.

## Decision

We **build a custom PSR-11 container** as CORE-02 (`SovereignStack\Core\Container`) with four explicit features: (1) constructor autowiring via `ReflectionClass`, (2) PHP 8.3 Attributes for explicit service configuration, (3) a `CompilerPass` system that flattens the resolution graph into a cached PHP array for production, and (4) circular dependency detection that throws `CircularDependencyException` rather than stack-overflowing. The container depends only on `psr/container: ^2.0` at runtime; PHP-DI, Symfony DI, and Laravel Container are explicitly rejected.

The custom container's `ContainerInterface` extends `Psr\Container\ContainerInterface` and adds `bind(string $id, mixed $concrete = null, bool $singleton = false): void` and `make(string $id, array $parameters = []): mixed`, mirroring the contract already declared in `docs/blueprints/Core/CORE-02.md`. Resolution is two-phase: a development-mode reflective path (slow but correct) and a production-mode compiled path (reads from a flat `services.php` array generated by `CompilerPass`).

## Alternatives Considered

| Alternative | Pros | Cons | Verdict |
|---|---|---|---|
| **PHP-DI 7.x** (`php-di/php-di`) | Battle-tested; widely adopted (10k+ stars); excellent autowiring; supports PHP 8 attributes; built-in lazy injection; well-documented compiler pass system | Adds ~2,500 LOC of third-party code to the most-depended-on Core tier; resolution semantics are PHP-DI's, not ours; circular dependency detection exists but throws `DependencyException` whose message format we cannot control; future SuperPHP `@persist` scope integration would require monkey-patching PHP-DI's `DefinitionSource` | Rejected — supply-chain and semantic-control costs outweigh the implementation savings |
| **Symfony DI 7.x** (`symfony/dependency-injection`) | Full-featured; mature compiler pass system; XML/YAML/PHP config; power-user features (service locators, tagged iterator, autoconfigure); backed by Symfony Corp's long-term support | Pulls in `symfony/polyfill-*`, `psr/container`, `symfony/deprecation-contracts` as transitive deps; the full Symfony DI bundle is ~30k LOC; configuration is XML/YAML-centric, conflicting with the attribute-driven model in CORE-02's spec; heavyweight for a Core-tier primitive | Rejected — too heavy; the dependency-injection graph is too central to delegate to a full-stack framework component |
| **Laravel Container 11.x** (`illuminate/container`) | Excellent developer ergonomics; `makeWith()` and `when()` APIs are ergonomic; widely used | Tied to the Laravel ecosystem (`illuminate/contracts` transitively); SemVer follows Laravel's release train (annual majors); the Laravel container does not have a true compiler pass (it resolves reflectively at runtime); incompatible with the "sovereign stack, no framework" principle | Rejected — anti-tenant-isolation (Laravel assumptions leak); no compile step |
| **League Container 4.x** (`league/container`) | Lightweight PSR-11; service providers; reflection-based autowiring; smaller than PHP-DI | Smaller community than PHP-DI; no first-class compiler pass (only "service providers" which are runtime); circular detection is weak; effectively abandoned upstream (last release: 2023-12) | Rejected — maintenance risk on the critical path |
| **No container (manual wiring / service locator)** | Zero lines of code to write; zero dependencies | Manual wiring defeats the testability that the Hub tier's design assumes; service locators are widely considered an anti-pattern; would force every Hub blueprint to roll its own resolution logic | Rejected — the Hub tier cannot be built without a container |

## Consequences

**Positive:**
- Total semantic control: the `CircularDependencyException` message, the compiler pass extension point, and the attribute discovery mechanism all match the Sovereign Stack's conventions exactly. No third-party behavior to work around.
- Minimal dependency surface: `composer require psr/container:^2.0` is the entire production dependency. SBOM is short, supply-chain audit is trivial, and CVEs in third-party DI libraries cannot affect us.
- The compiler pass architecture aligns with the OPcache preload strategy in ADR-010: a flattened `services.php` array preloads cleanly, whereas reflection-based containers do not.

**Negative:**
- We must build and maintain a reflection layer, a compiler pass system, a circular-dependency detector, and a full PSR-11 conformance test suite ourselves. Finding 8 in `00_CRITIQUE.md` is unambiguous: CORE-02 is the *single* highest-priority PR in the system, and until it lands, the entire Hub tier is blocked.
- No community extensions: any future integration (e.g. a Symfony bundle adapter for legacy apps) must be written by us. The SuperPHP `@persist` scope handling (CORE-12) will require container-side support that we own end-to-end.
- Fewer eyes on the code than PHP-DI; bugs in the reflection layer (e.g. union types, intersection types, `readonly` properties) must be caught by our own tests.

**Neutral:**
- The container's compiler-pass output format must be documented and versioned (it is consumed by the deployment pipeline; changing the on-disk format is a SemVer major).
- The PSR-11 conformance test suite (from `psr/container`'s official `container-interop/impl-test` fork) becomes a permanent CI requirement.
