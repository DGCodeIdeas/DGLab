# ADR-010: OPcache Preload Strategy for Core-Tier Classes

**Status:** Accepted
**Date:** 2026-08-04
**Deciders:** DGLab architecture team

## Context

The disapproved CORE-01 blueprint (per `00_CRITIQUE.md` Finding 4 — "Approved Is Not a Proxy for More Substantive", whose evidence notes the disapproved CORE-01 contained "performance budgets tied to OPcache preload") referenced OPcache preload as part of the orchestrator's runtime strategy. That reference was stripped when CORE-01 was rewritten as the Vision B polyrepo orchestrator, but the observation — that OPcache preload (PHP 7.4+) can dramatically reduce cold-start latency by pre-loading and pre-linking classes at PHP-FPM startup — remains operationally important.

Finding 19 in `00_CRITIQUE.md` flags "Why OPcache preload is enabled (referenced in disapproved CORE-01 but not decided)" as undocumented. The current production deployment (`render.yaml` + `Dockerfile`) runs `php -S 0.0.0.0:80 -t docs/architecture/origin` — the PHP built-in dev server, which has no OPcache and no preload. DEPLOY-01 will deploy real PHP-FPM services, and the question of whether to enable preload, what to preload, and how to maintain the preload script becomes load-bearing.

Three forces shape the choice. First, the "Hello World < 10ms" target (CORE-18) and "auth check < 1ms" target (HUB-04) require that every class on the request hot path be loaded, parsed, and linked before the first request arrives. Without preload, the first request after a PHP-FPM worker spawn pays a ~50ms class-loading and JIT-compile penalty — breaking the 10ms budget. Second, the custom container (ADR-002) compiles to a flat `services.php` array, the SuperPHP compiler (ADR-005) emits preload-friendly PHP, and the event dispatcher (CORE-03) is a small set of frequently-resolved classes — all preload candidates by construction. Third, PHP 8.3's preload is stable and well-documented; the cost is maintaining the preload script, not implementing it.

## Decision

We enable **OPcache preload in production** via `opcache.preload=/var/www/app/preload.php` in `php.ini`, with a preload script that pre-loads all Core-tier classes (`SovereignStack\Core\*`), the CORE-01 Orchestrator classes (`SovereignStack\Orchestrator\*`), the CORE-03 Event Dispatcher (already implemented), and the compiled container output (`storage/framework/services.php` once CORE-02 lands). The preload script is auto-generated by CORE-20 (Sovereign Forge) from every installed Composer package's `autoload-classmap.php`, filtered to the Core + Hub-tier namespaces. Hub-tier classes are preloaded only when their package is installed; Spoke-tier classes are never preloaded (request-scoped, would bloat worker memory).

The PHP-FPM configuration sets `opcache.preload_user=www-data` (required since PHP 7.4: preload cannot run as root). Deploying a new build requires a `systemctl reload php8.3-fpm` to re-execute the preload script; rolling deploys must drain in-flight requests before the reload, per DEPLOY-01's rolling-update strategy.

## Alternatives Considered

| Alternative | Pros | Cons | Verdict |
|---|---|---|---|
| **No preload (default OPcache only)** | Simpler `php.ini`; no preload script to maintain; no PHP-FPM reload required on deploy | Cold-start penalty: first request after a worker spawn pays ~50ms for class loading + JIT warmup, breaking the CORE-18 "Hello World < 10ms" budget; the compiled container's `services.php` is loaded lazily, adding ~5ms to the first authenticated request | Rejected — cold-start penalty is incompatible with the documented performance budgets |
| **JIT only (PHP 8.0+ JIT, no preload)** | JIT compiles hot methods at runtime; no PHP-FPM reload required | JIT warms up only after a method crosses the hotness threshold — first N requests pay interpretation cost; JIT does not preload class definitions; tracing mode needs ~1,000 requests before steady state | Rejected alone — JIT and preload are complementary; we enable both |
| **Preload only frequently-used classes** (just Container, Kernel, Router) | Smallest memory footprint (~5 MB); fastest preload execution; minimum maintenance surface | Misses the long tail of Core-tier classes on the hot path (event listeners, error handlers, log formatters); a class not on the list pays full cold-start cost on first touch; the "frequently-used" boundary is fuzzy and drifts as the codebase evolves | Rejected — too narrow; the chosen scope (all Core + installed Hub classes) is the right balance |
| **Preload everything (all installed Composer packages)** | Maximum cold-start improvement; no judgment calls | Worker memory explodes (preloading Laravel/Symfony/Doctrine can consume 100+ MB per worker); preloading Spoke-tier classes used in one request per thousand is wasteful | Rejected — selective preload of Core + Hub tiers is the correct scope |
| **APCu as a substitute for preload** | APCu can cache parsed bytecode across requests (per-process); no PHP-FPM reload | APCu is per-process, not shared across workers — every worker re-loads classes on first use; APCu does not pre-link class inheritance; APCu's user-cache API is unrelated to class loading | Rejected — solves a different problem |

## Consequences

**Positive:**
- Cold-start latency drops from ~50ms (class loading + JIT warmup) to ~5ms (preload + JIT pre-warmed). The CORE-18 "Hello World < 10ms" target becomes achievable on the first request after a worker spawn, not just the 100th. (Estimated 30–50% faster first request; to be measured per Governance Rule 2.)
- The compiled container (CORE-02's `services.php`) is preloaded into every worker before the first request. The first authenticated request pays no container-compilation cost, satisfying HUB-04's "auth check < 1ms" target from request #1.
- Class inheritance is pre-linked: PHP's preload resolves parent classes, interfaces, and traits at preload time, so the first request does not pay the `ReflectionClass` lookup cost.
- Worker memory is predictable: every worker starts with the same ~30 MB of preloaded Core + Hub classes.

**Negative:**
- Every deploy requires a `systemctl reload php8.3-fpm` (or `SIGUSR2`). This must be wired into DEPLOY-01's rolling-update playbook: drain the worker, reload, re-add to the pool. A naive deploy that just swaps files serves stale classes (preloaded classes are immutable per worker). **Preload errors are fatal**: if the preload script throws, PHP-FPM refuses to start, blocking the deploy.
- The preload script is a maintenance surface: every new Core-tier class must be on the preload list (auto-generated by CORE-20 from Composer's classmap, but a class added outside the expected namespace pattern will silently not be preloaded).
- Preload increases worker memory baseline: ~30 MB before serving any request; under pressure, PHP-FPM may kill workers via `pm.max_children` exhaustion. Preloaded classes cannot be unloaded — a single-class hotfix requires reloading the entire pool.

**Neutral:**
- `opcache.preload_user` must be set (typically `www-data`); PHP refuses to preload as root. One-time `php.ini` setting.
- `opcache.memory_consumption` must fit preloaded classes plus request-time cache. Default 128 MB suffices for Core + Hub; Spoke-heavy deployments may need 256 MB.
