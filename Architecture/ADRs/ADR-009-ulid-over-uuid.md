# ADR-009: ULID for All Entity IDs

**Status:** Accepted
**Date:** 2026-08-04
**Deciders:** DGLab architecture team

## Context

The HUB-01 blueprint ("Global Configuration & Feature Flags") stores dynamic tenant-specific overrides in a database table whose primary key is documented as `CHAR(26)` — a 26-character ASCII string that exactly matches the canonical ULID (Universally Unique Lexicographically Sortable Identifier) encoding. This is the strongest signal in the existing repo that ULIDs are the intended primary-key format, but the decision is nowhere documented. Finding 19 in `00_CRITIQUE.md` flags "Why ULID over UUID (used in HUB-04 per the prior analysis but not decided)" as one of the ten undocumented architectural decisions blocking confident maintenance. The HUB-04 blueprint uses `Authenticatable::getAuthIdentifier(): mixed` — the `mixed` return type hides the actual identifier format, so any consumer can silently assume a UUID, an integer, or a string.

Three forces shape the choice. First, the polyrepo architecture (ADR-001) means every Hub and Spoke generates IDs independently — there is no central sequence allocator, so identifiers must be collision-free without coordination. UUID v4 (random) and ULID both satisfy this, but auto-increment integers do not. Second, every entity is multi-tenant (per HUB-21's row-level isolation), so IDs appear in URLs (`/api/v1/users/{id}`), in JWT subject claims (`sub` per RFC 7519), in audit log entries (HUB-06), and in cache keys (HUB-02 via ADR-006). A 26-character ASCII identifier is URL-safe, JWT-safe, and Redis-safe. Third, index locality matters at scale: a B-tree index on a monotonically increasing key has better cache behavior than on a random key, because new rows cluster at the right edge of the index rather than scattering across leaf pages. UUID v4 is fully random (bad for B-tree locality); ULID is time-prefixed (good for B-tree locality).

## Decision

We adopt **ULID** (Universally Unique Lexicographically Sortable Identifier, 26-character Crockford Base32 encoding, 128-bit payload = 48-bit millisecond timestamp + 80-bit randomness) as the canonical identifier format for every entity: users, tenants, sessions, audit log entries, feature flags, cache-tag namespaces, queue jobs, and Spoke-level resources. Primary-key columns are typed `CHAR(26)` (or `bpchar(26)` on PostgreSQL when that driver is enabled) with a `CHECK` constraint enforcing the Crockford Base32 alphabet and a unique constraint. Foreign-key columns are likewise `CHAR(26)`. The `readonly` PHP 8.3 property `id` on every entity is typed `string`; the value is generated by the repository at insert time using `symfony/uid`'s `Ulid` factory (or `RobThree/UUID`).

UUID v4 is rejected. UUID v7 (RFC 9562, April 2024) is a legitimate successor and is tracked as a future migration candidate, but ULID has broader library support in the PHP ecosystem today and the migration from ULID to UUID v7 is a SemVer major for every Hub package. Auto-increment integers are rejected unconditionally.

## Alternatives Considered

| Alternative | Pros | Cons | Verdict |
|---|---|---|---|
| **UUID v4** (`ramsey/uuid`, RFC 4122) | Universal; well-understood; every language has a library; 36-char canonical form; no clock dependency | Fully random — terrible B-tree index locality (every insert lands at a random leaf page, causing page splits); 36-char form is longer than ULID's 26 chars (40% larger primary key, secondary indexes, foreign keys, URL slugs); not lexicographically sortable | Rejected — index locality is a real cost at scale; sortability is a free feature we should not throw away |
| **UUID v7** (RFC 9562, April 2024 — time-sortable) | Time-prefixed (good locality, like ULID); IETF-standardized; PHP support via `symfony/uid` `UuidV7` and `ramsey/uuid` 4.6+ | Standard is recent (April 2024) — library support still maturing (e.g. `doctrine/dbal` type registration incomplete); 36 chars is longer than ULID's 26; spec allows variable timestamp precision creating implementation divergence | Rejected for now; reconsider as a SemVer major migration once UUID v7 library support stabilizes (target: 2027) |
| **Auto-increment integer** (`SERIAL`/`AUTO_INCREMENT`) | Smallest storage (4 or 8 bytes); fastest index lookups; human-friendly; trivially sortable | Requires a central sequence allocator — impossible in a polyrepo where multiple Hub services insert rows concurrently; leaks row-count information (users can guess how many others exist); resharding by tenant ID range is impossible (sequential IDs are not tenant-scoped) | Rejected unconditionally — does not work in the polyrepo + multi-tenant model |
| **Snowflake ID** (Twitter, 64-bit, time-prefixed) | Compact (fits in a `BIGINT`); time-sortable; widely used at scale (Twitter, Discord, Instagram) | Requires a worker-ID allocator (every node needs a unique worker ID — operational burden); 64-bit ceiling means ~69 years of timestamps before rollover; not human-readable in URLs; weaker PHP ecosystem support | Rejected — the worker-ID allocation requirement conflicts with the polyrepo + multi-tenant model |
| **NanoID** (`hidehalo/nanoid-php`, 21-char URL-safe) | Shorter than ULID (21 chars); URL-safe; configurable alphabet | Not sortable — purely random, same B-tree locality problem as UUID v4; no standard encoding | Rejected — sortability is a feature we want |

## Consequences

**Positive:**
- Lexicographic sortability means `ORDER BY id` returns rows in creation order without a separate `created_at` column. This simplifies every audit-log query (HUB-06), every paginated API response, and every "give me the latest N" query.
- B-tree index locality is excellent: new rows append to the right edge of the index, page splits are rare, and write throughput scales linearly with insert rate. Materially better than UUID v4 at high write volume (HUB-06 audit log, HUB-09 event store).
- The 26-char ASCII Crockford Base32 encoding is URL-safe (no `+`, `/`, or `=`), JWT-safe (no JSON escaping), Redis-safe (no special characters in cache keys), and SQL-safe (no quote escaping).
- Collision-free without coordination: 80 bits of randomness per millisecond gives a < 10⁻⁶ probability of collision per billion IDs generated in the same millisecond (birthday-bound).

**Negative:**
- 26 chars is larger than a `BIGINT` (8 bytes) or a binary UUID (16 bytes). Stored as `CHAR(26)`, a ULID occupies 26 bytes plus the per-row fixed-width overhead — roughly 3× the storage of a binary UUID. Every primary key, foreign key, and secondary index pays this cost. For high-volume tables (HUB-06 audit log, HUB-09 event store), this is a real disk-space concern.
- ULID is a community spec (canonical reference is `ulid/javascript`, not an RFC). Cross-language library implementations occasionally diverge on edge cases (e.g. same-millisecond monotonicity). The Sovereign Stack must standardize on one PHP library (`symfony/uid` Ulid) and document that choice.

**Neutral:**
- The `CHAR(26)` column type and the Crockford Base32 `CHECK` constraint must be applied to every primary-key migration. CORE-20 (Sovereign Forge) should scaffold this automatically in its migration generator.
- The PHP `string` type for IDs means static analysis (PHPStan) cannot distinguish a ULID from any other string. A future `Ulid` value object (wrapping `string`) is recommended for type safety but is not required by this ADR.
