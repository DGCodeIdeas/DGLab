    39→
    40→The deeper structural problem: a single global build sequence cannot express that rings have fundamentally different natures, and a single DAG cannot distinguish architectural intent from implementation reality. The original ADR-021 (2026-09-30) ratified the 13-edge verified DAG as "authoritative" and the 45-edge declared view as "intent, not authoritative for admission." SAAI and Z.ai independently identified this as a false choice — both DAGs are authoritative, for different questions.
    41→
    42→This amendment establishes the **two-DAG governance model** that fixes these defects at the root.

    44→## Decision
    45→
    46→**Adopt a tier-stratified build order with two-DAG governance.** Each tier owns two authoritative DAGs with different scopes: a **Declared Architecture DAG** (architectural intent) and a **Verified Implementation DAG** (repository reality). Build orders are generated artifacts derived from both DAGs plus SDLC admission state — not independently authored. The SDLC's admission rule uses an `Eligible(X)` formula that gates admission on dependency closure + capability prerequisites + architecture gate + SDLC admission.

    58→### 2. Four Edge Types + Requiredness Dimension
    59→
    60→**Edge types** describe HOW the dependency works (mechanics + delivery semantics). **Requiredness** describes WHETHER it's mandatory (gating decision). These are orthogonal dimensions — an edge can be COMPILE+REQUIRED, COMPILE+OPTIONAL, RUNTIME+REQUIRED, etc.
    61→
    62→**Edge types** (exactly one per edge):
    63→
    64→| Edge type | Meaning | Example |
    65→|---|---|---|
    66→| **COMPILE** | Consumer requires target for construction/compilation/package assembly | `C10 → C09` (Logger requires Config via composer) |
    67→| **RUNTIME** | Consumer requires target while executing its runtime behavior | `C18 → RUNTIME-01` (Kernel needs FrankenPHP worker) |
    68→| **INTEGRATION** | Consumer depends on an external/system boundary being available and correctly wired | `C19 → MySQL`, `C14 → S3` |
    69→| **CAPABILITY** | Consumer requires a capability supplied by the target, without necessarily having a direct implementation dependency | `C19 → HUB-04` (DBAL enables Identity) |
    70→
    71→**Requiredness** (independent of edge_type):
    72→
    73→| Value | Meaning |
    74→|---|---|
    75→| **REQUIRED** | Missing target prevents the consumer from satisfying the relevant architectural gate |
    76→| **OPTIONAL** | Consumer remains valid without the target; target provides an optional enhancement/path |
    77→
    78→**This separation is critical.** `DECLARED_ONLY` (verification status) is NOT the same as `OPTIONAL` (requiredness). The edge `C18 → C17` is DECLARED_ONLY (C17 not yet implemented) but REQUIRED (production gate requires C17). Conflating these would cause a future generator to infer `verified=false → OPTIONAL → doesn't gate` — missing the C17 production gate requirement entirely.
    79→
    80→### 3. Two-DAG Governance Model (LOCKED)
    81→
    82→**Each tier owns two authoritative DAGs with different scopes:**
    83→
    84→| DAG | Authority | Source | Drives |
    85→|---|---|---|---|
    86→| **DECLARED DAG** (e.g., `CORE-DECLARED-DAG.md`) | Architectural intent ("should be") | Blueprints, ADRs, SPECs, declared `Upward` dependencies, capability contracts | Capability planning, architecture gates, identifying missing implementation work |
    87→| **VERIFIED DAG** (e.g., `CORE-VERIFIED-DAG.md`) | Repository reality ("is proven") | Composer manifests + PHP namespace imports + filesystem/package structure + generated implementation metadata + verified integration tests | Build eligibility, package-level ordering, SDLC admission |
    88→
    89→**Neither DAG overrides the other.** They answer different questions. The naming makes the authority boundary obvious — no future engineer asks "which one is the real DAG."
    90→
    91→```
    92→                 ARCHITECTURE
    93→                      │
    94→             ┌────────┴────────┐
    95→             ▼                 ▼
    96→       DECLARED DAG       VERIFIED DAG
    97→       "should be"         "is proven"
    98→             │                 │
    99→             └────────┬────────┘
   100→                      ▼
   101→                SDLC ADMISSION
   102→                      │
   103→             ┌────────┴────────┐
   104→             ▼                 ▼
   105→       Capability Gates    Implementation Gates
   106→             │                 │
   107→             └────────┬────────┘
   108→                      ▼
   109→               Build Eligibility
   110→```

   112→### 4. Four Edge Status Categories (LOCKED)
   113→
   114→Each edge's status is determined by comparing the declared and verified DAGs:
   115→
   116→| Status | Declared | Verified | Meaning | Action |
   117→|---|---|---|---|---|
   118→| `VERIFIED` | ✓ | ✓ | Implemented architectural dependency | None — healthy |
   119→| `DECLARED_ONLY` | ✓ | ✗ | Architectural work still required | Implement to close the gap |
   120→| `UNDECLARED_VERIFIED` | ✗ | ✓ | Architectural drift — investigate | Declare the edge or remove the dependency |
   121→| `INVALID` | ✗ | ✗ | No dependency | Prevents noise accumulation |
   122→
   123→**Example:** `CORE-18 → CORE-17` is `DECLARED_ONLY` — the blueprint declares the dependency but C17 is not implemented. The kernel's `Stub/ProviderRegistryInterface.php` is the evidence of the declared-but-unverified edge.
   124→
   125→### 5. Machine-Readable Edge Metadata Schema (LOCKED)
   126→
   127→Each edge is a structured record with 8 fields across 4 dimensions:
   128→
   129→```yaml
   130→source: CORE-18          # consuming component
   131→target: CORE-17          # consumed component
   132→edge_type: RUNTIME       # COMPILE | RUNTIME | INTEGRATION | CAPABILITY (exactly one)
   133→requiredness: REQUIRED    # REQUIRED | OPTIONAL (independent of edge_type)
   134→declared: true            # bool — architecture declares this edge
   135→verified: false           # bool — repository evidence confirms this edge
   136→status: DECLARED_ONLY    # DERIVED from (declared, verified): VERIFIED | DECLARED_ONLY | UNDECLARED_VERIFIED | INVALID
   137→gates:                   # LIST — one or more gate values this edge affects
   138→  - RUNTIME
   139→  - PRODUCTION
   140→evidence:                # evidence supporting the edge's current state (declaration evidence if verified=false, verification evidence if verified=true)
   141→  - packages/core/kernel/src/Stub/ProviderRegistryInterface.php
   142→```
   143→
   144→**Four dimensions:**
   145→- `edge_type` — HOW the dependency works (mechanics)
   146→- `requiredness` — WHETHER it's mandatory (gating decision)
   147→- `declared` + `verified` → `status` (derived) — evidence state
   148→- `gates` — WHAT readiness gates it affects (consequences; list, not scalar — one edge can affect multiple gates)
   149→- `evidence` — WHY (proof sources supporting the current state)
   150→
   151→**Evidence definition:** `evidence` is **evidence supporting the edge's current state**, not necessarily verification evidence. For `DECLARED_ONLY` edges, evidence is the architectural declaration (blueprint file path). For `VERIFIED` edges, evidence is the code proof (composer.json, use statement, test). For `UNDECLARED_VERIFIED`, evidence proves the repository relationship that architecture hasn't declared.
   152→
   153→This makes the DAG **machine-generated and machine-verified** — not hand-maintained. Drift between declared and verified becomes automatically detectable. Future tooling (`scripts/generate-verified-dag.py`, `scripts/generate-declared-dag.py`, `scripts/compare-dags.py`) will produce and compare these records automatically.
   154→
   155→### 6. Three-Axis Status Model (replaces single "depth" number)
   156→
   157→The current SDLC depth scale (1-6) conflates three orthogonal concepts. This ADR establishes a three-axis model:
   158→
   159→| Axis | What it measures | Evidence | Example |
   160→|---|---|---|---|
   161→| `implementation_depth` | Does the code exist + pass PHPUnit/PHPStan? | Source files + test results | C18: depth 2 (code exists, tests pass) |
   162→| `integration_completeness` | Is the assembled-system wiring complete? | Verified DAG edges + stub analysis | C18: PARTIALLY WIRED (C17 stub = no-op boot) |
   163→| `production_gate` | What's required for production readiness? | Declared DAG edges not yet verified | C18: C17 required (provider system must exist) |
   164→
   165→This applies beyond Core — Hub and Spoke packages will have the same pattern (unit tests pass while assembled-system capabilities remain incomplete).
   166→
   167→**C18 example (the clearest case):**
   168→- `implementation_depth`: 2 (Kernel code exists, 15 PHPUnit tests pass)
   169→- `integration_completeness`: PARTIALLY WIRED (`EmptyProviderRegistry` no-op stub for C17)
   170→- `production_gate`: C17 required (provider system must exist before boot is real)
   171→
   172→### 7. The `Eligible(X)` Admission Rule
   173→
   174→```
   175→Eligible(X) =
   176→    every REQUIRED incoming edge has its required gates satisfied
   177→        (REQUIRED edges gate admission; OPTIONAL edges do not)
   178→    AND required CAPABILITY dependencies are delivered
   179→        (REQUIRED CAPABILITY edges into X have targets delivered)
   180→    AND architecture gate passed
   181→        (interfaces frozen + fitness functions pass + lifecycle/resource guarantees)
   182→    AND SDLC admission granted
   183→        (capacity, findings, throughput calibration, cooldown status)
   184→```
   185→
   186→**Key principle:** `edge_type` tells us HOW to evaluate the dependency. `requiredness` determines WHETHER it gates. `gates` tells us WHAT's affected. These are cleanly separated — `edge_type` never itself determines whether an edge gates admission; `requiredness` does.
   187→
   188→### 8. Six-Criteria Capability Gate
   189→
   190→A tier is "at gate" when ALL of:
   191→1. Required dependency closure exists (REQUIRED edges satisfied)
   192→2. Required capability closure exists (REQUIRED CAPABILITY edges delivered)
   193→3. Interfaces frozen (export-allow-list enforced)
   194→4. Architecture fitness passes (ring-boundary, contamination, freeze tests)
   195→5. Lifecycle/resource guarantees pass (worker recycling, signal handling — for runtime-touching tiers)
   196→6. Required application path is executable (for Application tier: `anvilctl verify all` against staging)
   197→
   198→**Tier population ≠ Required production closure.** The "required closure" is a SUBSET of the tier — the packages on the path to a production-deployable application — not the entire tier population. A tier is "at gate" when the required production closure satisfies the six criteria, not when ALL packages in the tier are complete. A tier can be at-gate with 12 of 20 Core blueprints at depth 2 if those 12 constitute the required production closure for the application path being deployed.
   199→
   200→### 8.5. Multigraph Semantics (LOCKED)
   201→
   202→The DAG is a **multigraph**: the same source/target pair may have multiple edges with different `edge_type` values. For example:
   203→
   204→```
   205→CORE-10 ──COMPILE──────► CORE-09   (Logger's composer.json requires Config)
   206→CORE-10 ──CAPABILITY───► CORE-09   (Logger needs Config's values to function)
   207→```
   208→
   209→Each edge independently carries `requiredness`, `evidence` state, and `gates` impact. This is preferable to creating an overloaded edge whose semantics become difficult for generators to reason about.
   210→
   211→**Generator edge identity:** `source + target + edge_type`. The generator's edge identity is NOT `source + target` — otherwise it could overwrite the COMPILE edge when it discovers a CAPABILITY edge between the same components.

   307→## Consequences
   308→
   309→### Positive
   310→
   311→1. **Two-DAG governance prevents drift.** Declared and verified DAGs answer different questions; both are authoritative. Drift between them becomes automatically detectable via the four edge status categories.
   312→2. **Runtime substrate becomes visible to the SDLC.** The missing layer (Anvil v3, systemd timers) is now a first-class tier with depth requirements.
   313→3. **Build orders derived, not hand-numbered.** Topological waves calculated from verified edges eliminate arbitrary sequencing.
   314→4. **Three-axis status model** separates implementation depth from integration completeness from production gate — no more conflating "tests pass" with "production ready."
   315→5. **Machine-readable edge metadata** enables future tooling to auto-generate DAGs, compare them, and detect drift.
   316→6. **INDEX authority evolution** prevents manual maintenance of derived facts — "never manually maintain what the repo can derive."
   317→7. **HUB-32 unblocks 4 ELQ ISPOKEs** and future AI-consuming ESPOKEs.
   318→
   319→### Negative
   320→
   321→1. **Documentation surface grows.** Each tier gets two DAGs + capability DAG + build order. Mitigated by generation from blueprints + repository evidence (not hand-maintained).
   322→2. **HUB-10 and HUB-25 relocation** breaks external references. Blueprints are marked SUPERSEDED with redirect pointers.
   323→3. **DAG generator tooling not yet built.** The two-DAG model is ratified but the scripts (`generate-verified-dag.py`, `generate-declared-dag.py`, `compare-dags.py`, `generate-build-order.py`) are tracked as future tasks. Until they exist, DAGs are hand-maintained markdown.
   324→4. **Known latent defects (§21) are documented but not fixed.** The C04↔C05 namespace collision and C17 forward-declaration stub are tracked for future ADRs.
   325→
   326→### Neutral / Gated
   327→
   328→1. **SDLC-AGRD v4.0 rewrite** — implements the Eligible(X) admission rule + per-tier laps. Tracked as a separate PR.
   329→2. **DAG generator scripts** — `scripts/generate-verified-dag.py` etc. Tracked as future tasks.
   330→3. **Cross-tier admission-gate fitness function** — new FF in `scripts/fitness/`. Tracked as a separate PR.
   331→4. **Hub/Spoke/Deploy/Runtime per-tier DAGs** — Core is first; others follow the same two-DAG methodology.

   341→| **Per-tier depth scales** | Subsumed by the three-axis status model + Capability DAG. |
   342→| **45-edge declared DAG as sole authority** | Not honest about current state — would ignore the fact that most edges are not yet verified in code. |
   343→| **13-edge verified DAG as sole authority** | Loses architectural intent — would miss `C18 → C17` (declared but not yet implemented) and other future-looking edges. |
   344→| **Single-enum edge_type (original ADR-021 §2)** | Conflated three orthogonal dimensions: dependency mechanics (COMPILE/RUNTIME/INTEGRATION), delivery semantics (CAPABILITY), and requiredness (OPTIONAL). A DECLARED_ONLY edge would be implicitly treated as OPTIONAL, missing REQUIRED production gate dependencies like C17. |
   345→| **Scalar `gate` field** | Forces choosing one gate when an edge can affect multiple gates (e.g., C18→C17 affects both RUNTIME and PRODUCTION). List `gates` captures the full gate impact set. |
