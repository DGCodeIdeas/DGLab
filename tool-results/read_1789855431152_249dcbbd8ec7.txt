    12→## Component Name
    13→Binary Encryption Envelope — `SovereignStack\Core\Crypto`
    14→
    15→## Description
    16→
    17→CORE-16 is the **cryptographic foundation** of the SovereignStack Core tier. It owns three concerns: (1) **authenticated symmetric encryption** of arbitrary plaintext strings, returned as a portable, versioned, base64-encoded "envelope" that bundles the key id, initialization vector, ciphertext, and AEAD tag in a single self-describing token; (2) **password hashing** via Argon2id per ADR-008, exposed through a `PasswordHasher` wrapper that delegates to PHP's native `password_hash()` / `password_verify()` / `password_needs_rehash()` triad; and (3) **key derivation** via HKDF-SHA256 (RFC 5869), exposed through a `Hasher` for callers that need to derive subkeys from a master key. The component is unambiguously the cryptographic primitive; it is **not** the "Logging & Observability" component the stale evaluation layer (`docs/evaluation/BLUEPRINT_RANKINGS.md`) labelled it (Finding 2). Logging is CORE-09; this component emits no log records itself and depends on CORE-09 only optionally (a PSR-3 `LoggerInterface` is accepted in the constructor for audit-trail purposes, but is **never** given raw key material, plaintext, or ciphertext — see Security Properties).
    18→
    19→The component exists because the SovereignStack has at least four consumers that need encryption: HUB-04 (Identity) — password hashing and JWT signing-key storage; HUB-20 (Vault) — application-level secret storage (OAuth tokens, API keys, payment credentials) above the database; BRIDGE-01 (Vanguard) — payload verification on inbound requests (per Finding 3, BRIDGE-01 depends on CORE-16, *not* CORE-09); and CORE-19 (DBAL) — optional column-level encryption for tenant PII. Allowing each consumer to pick its own cipher, mode, and key-management scheme produces the familiar drifts: cipher drift (some AES-256-CBC, some ChaCha20, some AES-128-CTR — none authenticated), IV drift (some reuse, some zero IVs, some too short), key drift (hard-coded in env, stored in plaintext DB columns, written to world-readable files). CORE-16 standardises all three: **AES-256-GCM** as the cipher (NIST SP 800-38D, AEAD — integrity-protected ciphertext by construction), **12-byte cryptographically random IVs** per encryption call (never reused with the same key), **versioned envelope format** (future cipher upgrades — e.g. AES-256-GCM-SIV, XChaCha20-Poly1305 — are possible without breaking stored payloads), and a **`KeyRegistry`** for multi-key management with non-disruptive rotation.
    20→
    21→What this component is **not**: it is not a full KMS (key-management service) — HUB-20 Vault owns the sealed-secret storage and rotation-orchestration layer above CORE-16; CORE-16's `KeyRegistry` is an in-process registry that holds keys loaded from the runtime environment (CORE-10 Config) or fetched from HUB-20, never a persistent secret store itself. It is not a public-key primitive — there is no RSA, no ECDSA signing surface here (JWT signing in HUB-04 uses `ext-openssl` directly per ADR-003, ES256 algorithm; CORE-16 owns only symmetric encryption, password hashing, and HKDF). It is not a hashing primitive for non-password data — `Hasher` exposes HKDF for key derivation, not SHA-256 for arbitrary checksums; consumers needing checksums use `hash('sha256', ...)` directly. It is not a random-source primitive — callers needing CSPRNG output use `random_bytes()` directly; CORE-16 uses it internally for IV generation but does not re-export it.

    35→## Architectural Design
    36→
    37→### Class Map
    38→
    39→| Class | Kind | Responsibility |
    40→|---|---|---|
    41→| `Encrypter` | `final class implements EncrypterInterface` | Main encryption service. Holds a `KeyRegistryInterface` instance. `encrypt($plaintext, $kid = null)` generates a 12-byte cryptographically random IV, encrypts via `openssl_encrypt($plaintext, 'aes-256-gcm', $key, OPENSSL_RAW_DATA, $iv, $tag)`, constructs an `Envelope` value object, returns `base64_encode(json_encode($envelope))`. `decrypt($payload)` reverses: base64-decode → JSON-decode → `Envelope` → look up key by `kid` in registry → `openssl_decrypt` → plaintext; throws `CryptoException` on tag mismatch (tamper detection). `rotateKey($newKid)` generates a fresh 32-byte key via `random_bytes(32)`, adds it to the registry, sets it active, and retains the previous key for decrypt-only operation until its TTL expires. |
    42→| `Envelope` | `final readonly class` | Value object. Four properties: `string $kid` (key identifier), `string $iv` (12 raw bytes, base64-encoded in JSON), `string $ciphertext` (raw ciphertext, base64-encoded in JSON), `string $tag` (16 raw bytes, base64-encoded in JSON). Plus `int $v` (envelope format version, currently `1`). Implements `JsonSerializable` so it round-trips through `json_encode` / `json_decode` cleanly. |
    43→| `KeyRegistry` | `final class implements KeyRegistryInterface` | Multi-key manager. Holds a map of `kid → raw 32-byte key` and an `activeKid` pointer. `getActiveKey()` returns the active kid (not the raw key — callers go through `getKey($kid)` to retrieve raw bytes). `getKey($kid)` returns the raw 32-byte key, throwing `CryptoException` if the kid is unknown or deactivated. `addKey($kid, $key)` registers a new key (the first added becomes active by default). `setActiveKey($kid)` promotes an existing key to ACTIVE and demotes the previous active key to RETAINED — used by `Encrypter::rotateKey()`. `deactivateKey($kid)` marks it as decrypt-only (still retrievable via `getKey`, but `getActiveKey` will never return it). Retention-TTL handled externally (HUB-20 Vault orchestrates destruction after TTL). |
    44→| `PasswordHasher` | `final class` | Argon2id wrapper. `hash(string $plaintext): string` delegates to `password_hash($plaintext, PASSWORD_ARGON2ID, $options)` with default `memory_cost=65536`, `time_cost=4`, `threads=2` per ADR-008 (RFC 9106 second-tier). `verify(string $plaintext, string $hash): bool` delegates to `password_verify()`. `needsRehash(string $hash): bool` delegates to `password_needs_rehash()` — used by HUB-04 to upgrade legacy bcrypt/PBKDF2 hashes on next login. Parameters configurable per-tenant via HUB-01 GlobalConfig; constraint: parameters can only ever be *increased* (enforced by `setOptions()` rejecting lower values). |
    45→| `Hasher` | `final class` | HKDF-SHA256 wrapper. `deriveKey(string $masterKey, string $info, int $length = 32): string` delegates to `hash_hkdf('sha256', $masterKey, $length, $info)`. Used by HUB-20 Vault for envelope-encryption key derivation (master KEK → per-secret DEK) and by HUB-04 for JWT signing-key derivation from the master `APP_KEY`. **Not** a password-hashing primitive — HKDF has no salt-and-iteration loop and is trivially brute-forceable for low-entropy inputs (see ADR-008 §Alternatives). |
    46→| `CryptoException` | `final class extends \RuntimeException` | Marker exception for all cryptographic failures: tag mismatch on decrypt, unknown kid, deactivated key used for encryption, key-length violation (raw key not 32 bytes for AES-256), invalid envelope JSON, base64 decode failure. Carries an `errorCode` string enum (`TAG_MISMATCH`, `UNKNOWN_KID`, `DEACTIVATED_KEY`, `INVALID_KEY_LENGTH`, `INVALID_ENVELOPE`, `BASE64_DECODE_FAILED`) for programmatic dispatch by callers and for HUB-06 Audit logging without leaking key material. |

    48→### Interface Contracts
    49→
    50→```php
    51→<?php
    52→declare(strict_types=1);
    53→
    54→namespace SovereignStack\Core\Crypto;
    55→
    56→/**
    57→ * Main encryption service contract.
    58→ *
    59→ * The encrypter produces a self-describing, versioned "envelope" —
    60→ * a base64-encoded JSON object containing the key id (kid), the
    61→ * 12-byte initialization vector, the ciphertext, and the 16-byte
    62→ * AEAD authentication tag. The envelope is the only payload format
    63→ * the encrypter accepts on input or returns on output; raw
    64→ * ciphertext is never accepted.
    65→ *
    66→ * Invariants enforced by every implementation:
    67→ *
    68→ *  1. The IV is cryptographically random (12 bytes from random_bytes)
    69→ *     and is never reused with the same key. Implementations MUST
    70→ *     NOT accept a caller-supplied IV — IV generation is the
    71→ *     encrypter's responsibility.
    72→ *
    73→ *  2. The cipher is AES-256-GCM (AEAD). The authentication tag is
    74→ *     computed by OpenSSL and verified on decrypt; tag mismatch
    75→ *     throws CryptoException(TAG_MISMATCH) and returns no plaintext.
    76→ *
    77→ *  3. Key rotation is non-disruptive. Old keys remain in the
    78→ *     registry for decrypt-only operation until their TTL expires
    79→ *     and HUB-20 removes them; encrypting with a rotated key throws
    80→ *     CryptoException(DEACTIVATED_KEY).
    81→ *
    82→ *  4. The envelope is versioned. The current version is 1; future
    83→ *     versions may switch cipher (e.g. AES-256-GCM-SIV) without
    84→ *     breaking stored payloads — decrypt() dispatches on the
    85→ *     version field.
    86→ */
    87→interface EncrypterInterface
    88→{
    89→    /**
    90→     * Encrypt a plaintext string into a base64-encoded envelope.
    91→     *
    92→     * The caller does not see the IV, the tag, or the raw ciphertext —
    93→     * only the opaque envelope string. The envelope is safe to store
    94→     * in a database column, transmit over an untrusted channel (the
    95→     * ciphertext is integrity-protected), or hand to a downstream
    96→     * service.
    97→     *
    98→     * @param string $plaintext The plaintext to encrypt. Binary-safe;
    99→     *                          the encrypter treats the input as a
   100→     *                          byte string and does not interpret
   101→     *                          character encoding.
   102→     * @param string|null $kid  Optional key id. If null, the registry's
   103→     *                          active key is used. If non-null, the
   104→     *                          specified key must exist and not be
   105→     *                          deactivated; passing a deactivated kid
   106→     *                          throws CryptoException(DEACTIVATED_KEY).
   107→     *
   108→     * @return string The base64-encoded envelope:
   109→     *                base64(json({v,kid,iv,ciphertext,tag})).
   110→     *
   111→     * @throws CryptoException If the active key is missing, the kid
   112→     *         is unknown or deactivated, the key length is not 32
   113→     *         bytes, or OpenSSL reports a failure.
   114→     */
   115→    public function encrypt(string $plaintext, ?string $kid = null): string;
   116→
   117→    /**
   118→     * Decrypt a base64-encoded envelope back to the original plaintext.
   119→     *
   120→     * Reverses encrypt(): base64-decode the payload, JSON-decode the
   121→     * envelope, look up the key by kid in the registry, and call
   122→     * openssl_decrypt with the IV and tag from the envelope. The tag
   123→     * is verified by OpenSSL; a tag mismatch (tampered ciphertext,
   124→     * wrong key, truncated payload) throws CryptoException(TAG_MISMATCH)
   125→     * and returns no plaintext.
   126→     *
   127→     * @param string $payload The base64-encoded envelope returned by
   128→     *                        encrypt(). Binary-safe on the inside;
   129→     *                        the input itself is ASCII (base64).
   130→     *
   131→     * @return string The original plaintext.
   132→     *
   133→     * @throws CryptoException If the payload is not valid base64
   134→     *         (BASE64_DECODE_FAILED), the JSON is malformed or missing
   135→     *         required fields (INVALID_ENVELOPE), the kid is unknown
   136→     *         (UNKNOWN_KID), the key length is wrong (INVALID_KEY_LENGTH),
   137→     *         or the AEAD tag does not verify (TAG_MISMATCH).
   138→     */
   139→    public function decrypt(string $payload): string;
   140→
   141→    /**
   142→     * Rotate the active encryption key.
   143→     *
   144→     * Generates a fresh 32-byte key via random_bytes(32), adds it to
   145→     * the registry under $newKid, and sets it as the active key. The
   146→     * previous key is retained for decrypt-only operation; existing
   147→     * envelopes encrypted with the old key continue to decrypt
   148→     * successfully. New encrypt() calls use the new key.
   149→     *
   150→     * The caller is responsible for choosing $newKid — typically a
   151→     * ULID (per ADR-009) or a date-stamped identifier like
   152→     * "app-key-2026-08-04". The kid MUST be unique within the
   153→     * registry; passing an existing kid throws CryptoException.
   154→     *
   155→     * Key destruction (after TTL expiry) is HUB-20 Vault's
   156→     * responsibility — it calls KeyRegistry::deactivateKey() and
   157→     * later removes the key from the backing store. rotateKey()
   158→     * never destroys a key.
   159→     *
   160→     * @param string $newKid The key identifier for the new active key.
   161→     *
   162→     * @throws CryptoException If $newKid already exists in the registry,
   163→     *         or random_bytes() fails (extremely unlikely — signals
   164→     *         a broken CSPRNG and a non-recoverable runtime).
   165→     */
   166→    public function rotateKey(string $newKid): void;
   167→}
   168→
   169→/**
   170→ * Multi-key registry contract.
   171→ *
   172→ * The registry holds a map of kid → raw 32-byte key and an
   173→ * activeKid pointer. Keys can be in one of two states: ACTIVE
   174→ * (eligible for both encryption and decryption) or RETAINED
   175→ * (decrypt-only, after rotation).
   176→ *
   177→ * The registry never persists keys itself — it is an in-process
   178→ * cache. On process start, the registry is populated from the
   179→ * runtime environment (CORE-10 Config) or from HUB-20 Vault.
   180→ * Destruction-after-TTL is HUB-20's responsibility.
   181→ *
   182→ * Invariants:
   183→ *
   184→ *  1. There is always exactly one ACTIVE key. The registry
   185→ *     refuses to return from getActiveKey() if no key is active
   186→ *     (throws CryptoException).
   187→ *
   188→ *  2. Raw key material is never logged. The registry's __toString()
   189→ *     returns "KeyRegistry(<kid-count> keys, active=<kid>)" —
   190→ *     never the key bytes.
   191→ *
   192→ *  3. Key length is enforced on addKey(). Raw keys MUST be exactly
   193→ *     32 bytes (AES-256). Shorter or longer keys throw
   194→ *     CryptoException(INVALID_KEY_LENGTH).
   195→ */
   196→interface KeyRegistryInterface
   197→{
   198→    /**
   199→     * Return the kid of the currently active key.
   200→     *
   201→     * The active key is the one encrypt() uses when $kid is null.
   202→     * There is always exactly one active key after the first
   203→     * addKey() call.
   204→     *
   205→     * @return string The active kid.
   206→     *
   207→     * @throws CryptoException If no key is active (registry empty
   208→     *         or all keys deactivated).
   209→     */
   210→    public function getActiveKey(): string;
   211→
   212→    /**
   213→     * Return the raw 32-byte key for a given kid.
   214→     *
   215→     * Used by decrypt() to look up the key for an envelope. Works
   216→     * for both ACTIVE and RETAINED keys — a rotated key is still
   217→     * retrievable until HUB-20 destroys it after TTL expiry.
   218→     *
   219→     * @param string $kid The key identifier.
   220→     *
   221→     * @return string The raw 32-byte key.
   222→     *
   223→     * @throws CryptoException If $kid is unknown (UNKNOWN_KID).
   224→     */
   225→    public function getKey(string $kid): string;
   226→
   227→    /**
   228→     * Add a new key to the registry.
   229→     *
   230→     * The first key added becomes the active key by default.
   231→     * Subsequent keys are RETAINED until setActiveKey() is called
   232→     * (typically by Encrypter::rotateKey()).
   233→     *
   234→     * @param string $kid The key identifier. MUST be unique.
   235→     * @param string $key The raw 32-byte key. MUST be exactly 32
   236→     *                    bytes (CRYPTO_INVALID_KEY_LENGTH otherwise).
   237→     *
   238→     * @throws CryptoException If $kid already exists or $key is not
   239→     *         32 bytes.
   240→     */
   241→    public function addKey(string $kid, string $key): void;
   242→
   243→    /**
   244→     * Deactivate a key.
   245→     *
   246→     * Marks the key as RETAINED (decrypt-only). The key remains in
   247→     * the registry and is still retrievable via getKey(); it is no
   248→     * longer returned by getActiveKey(). If the deactivated key was
   249→     * the active key, getActiveKey() throws CryptoException until
   250→     * a new active key is set.
   251→     *
   252→     * @param string $kid The key identifier.
   253→     *
   254→     * @throws CryptoException If $kid is unknown.
   255→     */
   256→    public function deactivateKey(string $kid): void;
   257→
   258→    /**
   259→     * Designate an existing key as the active key.
   260→     *
   261→     * Used by Encrypter::rotateKey() to promote a newly-added key
   262→     * to ACTIVE. The previously active key (if any) is implicitly
   263→     * demoted to RETAINED — it remains in the registry and is still
   264→     * retrievable via getKey() for decrypt-only operation.
   265→     *
   266→     * @param string $kid The key identifier. MUST already exist in
   267→     *                    the registry (added via addKey()).
   268→     *
   269→     * @throws CryptoException If $kid is unknown.
   270→     */
   271→    public function setActiveKey(string $kid): void;
   272→}

   275→### Reference Implementation
   276→
   277→The complete `Encrypter` class:
   278→
   279→```php
   280→<?php
   281→declare(strict_types=1);
   282→
   283→namespace SovereignStack\Core\Crypto;
   284→
   285→use Psr\Log\LoggerInterface;
   286→use Psr\Log\NullLogger;
   287→
   288→/**
   289→ * AES-256-GCM authenticated encryption with versioned envelopes.
   290→ *
   291→ * The encrypter is the only entry point for symmetric encryption in
   292→ * the SovereignStack. It owns three concerns: IV generation, AEAD
   293→ * encryption via OpenSSL, and envelope serialisation. Key material
   294→ * is delegated to KeyRegistryInterface.
   295→ *
   296→ * The encrypter is stateless across calls — each encrypt() call
   297→ * generates a fresh IV and produces an independent envelope. The
   298→ * encrypter is safe to register as a singleton in CORE-02's DI
   299→ * container.
   300→ */
   301→final class Encrypter implements EncrypterInterface
   302→{
   303→    private const CIPHER = 'aes-256-gcm';
   304→    private const IV_LENGTH = 12;       // 96-bit IV per NIST SP 800-38D
   305→    private const KEY_LENGTH = 32;      // 256-bit key
   306→    private const ENVELOPE_VERSION = 1;
   307→
   308→    public function __construct(
   309→        private readonly KeyRegistryInterface $registry,
   310→        private readonly LoggerInterface $logger = new NullLogger()
   311→    ) {
   312→    }
   313→
   314→    public function encrypt(string $plaintext, ?string $kid = null): string
   315→    {
   316→        $effectiveKid = $kid ?? $this->registry->getActiveKey();
   317→        $key = $this->registry->getKey($effectiveKid);
   318→
   319→        if (strlen($key) !== self::KEY_LENGTH) {
   320→            throw CryptoException::invalidKeyLength($effectiveKid, strlen($key));
   321→        }
   322→
   323→        // 12-byte cryptographically random IV. NEVER reused with the
   324→        // same key (2^32 encryptions before collision risk per NIST).
   325→        $iv = random_bytes(self::IV_LENGTH);
   326→        $tag = '';
   327→
   328→        $ciphertext = openssl_encrypt(
   329→            $plaintext,
   330→            self::CIPHER,
   331→            $key,
   332→            OPENSSL_RAW_DATA,
   333→            $iv,
   334→            $tag
   335→        );
   336→
   337→        if ($ciphertext === false) {
   338→            // OpenSSL reports a failure — almost certainly a malformed
   339→            // key or a disabled mode. Log the kid (not the key) for
   340→            // triage, then throw.
   341→            $this->logger->error('openssl_encrypt failed', ['kid' => $effectiveKid]);
   342→            throw CryptoException::encryptionFailed($effectiveKid);
   343→        }
   344→
   345→        $envelope = new Envelope(
   346→            version: self::ENVELOPE_VERSION,
   347→            kid: $effectiveKid,
   348→            iv: $iv,
   349→            ciphertext: $ciphertext,
   350→            tag: $tag
   351→        );
   352→
   353→        $this->logger->debug('envelope encrypted', ['kid' => $effectiveKid, 'bytes' => strlen($plaintext)]);
   354→
   355→        return base64_encode(json_encode($envelope, JSON_THROW_ON_ERROR));
   356→    }
   357→
   358→    public function decrypt(string $payload): string
   359→    {
   360→        $decoded = base64_decode($payload, true);
   361→        if ($decoded === false) {
   362→            throw CryptoException::base64DecodeFailed();
   363→        }
   364→
   365→        try {
   366→            $data = json_decode($decoded, true, 4, JSON_THROW_ON_ERROR);
   367→        } catch (\JsonException $e) {
   368→            throw CryptoException::invalidEnvelope('json decode failed: ' . $e->getMessage());
   369→        }
   370→
   371→        if (!is_array($data)
   372→            || !isset($data['v'], $data['kid'], $data['iv'], $data['ciphertext'], $data['tag'])
   373→        ) {
   374→            throw CryptoException::invalidEnvelope('missing required fields');
   375→        }
   376→
   377→        if ((int) $data['v'] !== self::ENVELOPE_VERSION) {
   378→            // Future: dispatch on version field for cipher upgrades.
   379→            throw CryptoException::invalidEnvelope('unsupported envelope version: ' . $data['v']);
   380→        }
   381→
   382→        $kid = (string) $data['kid'];
   383→        $key = $this->registry->getKey($kid);
   384→
   385→        if (strlen($key) !== self::KEY_LENGTH) {
   386→            throw CryptoException::invalidKeyLength($kid, strlen($key));
   387→        }
   388→
   389→        $iv = base64_decode((string) $data['iv'], true);
   390→        $ciphertext = base64_decode((string) $data['ciphertext'], true);
   391→        $tag = base64_decode((string) $data['tag'], true);
   392→
   393→        if ($iv === false || $ciphertext === false || $tag === false) {
   394→            throw CryptoException::invalidEnvelope('inner base64 decode failed');
   395→        }
   396→
   397→        $plaintext = openssl_decrypt(
   398→            $ciphertext,
   399→            self::CIPHER,
   400→            $key,
   401→            OPENSSL_RAW_DATA,
   402→            $iv,
   403→            $tag
   404→        );
   405→
   406→        if ($plaintext === false) {
   407→            // Tag mismatch (tampered ciphertext, wrong key, truncated
   408→            // payload) — fail closed, return no plaintext.
   409→            $this->logger->warning('openssl_decrypt failed (tag mismatch)', ['kid' => $kid]);
   410→            throw CryptoException::tagMismatch($kid);
   411→        }
   412→
   413→        $this->logger->debug('envelope decrypted', ['kid' => $kid, 'bytes' => strlen($plaintext)]);
   414→
   415→        return $plaintext;
   416→    }
   417→
   418→    public function rotateKey(string $newKid): void
   419→    {
   420→        // generate a fresh 32-byte key from the CSPRNG.
   421→        $newKey = random_bytes(self::KEY_LENGTH);
   422→
   423→        // addKey() throws if $newKid already exists — the caller must
   424→        // choose a fresh identifier.
   425→        $this->registry->addKey($newKid, $newKey);
   426→
   427→        // The previous active key is implicitly demoted to RETAINED
   428→        // by the act of setting a new active key. KeyRegistry holds
   429→        // it for decrypt-only operation until HUB-20 destroys it.
   430→        $this->registry->setActiveKey($newKid);
   431→
   432→        $this->logger->info('encryption key rotated', ['new_kid' => $newKid]);
   433→    }
   434→}
   435→```

   567→### SQL DDL
   568→
   569→CORE-16 itself is **stateless** — it does not own a database table. The `KeyRegistry` is an in-process cache populated at boot from CORE-10 Config or HUB-20 Vault. Two downstream consumers persist CORE-16 output:
   570→

   644→## Integration Strategy
   645→
   646→**Upward — what CORE-16 consumes.** The encrypter constructor accepts a `KeyRegistryInterface` and an optional PSR-3 `LoggerInterface`. The registry is populated at boot by a CORE-17 Service Provider that reads `APP_KEY` (and per-tenant overrides) via CORE-10's `ConfigInterface` and, for envelopes that need to survive process restarts, fetches additional KEKs from HUB-20 Vault. The PSR-3 logger is used for *operational* audit trail (`info: encryption key rotated`, `warning: openssl_decrypt failed (tag mismatch)`, `error: openssl_encrypt failed`) — it is **never** given the raw key, plaintext, ciphertext, or tag (see Security Properties). Default is `new NullLogger()` so the encrypter works in contexts where CORE-09 Logging is not yet bootstrapped.
   647→
   648→**Downward — what consumes CORE-16.** Three direct consumers wire the encrypter via CORE-02 DI:
   649→
   650→```php
   651→// packages/core/providers/src/CryptoServiceProvider.php
   652→public function register(ContainerInterface $c): void
   653→{
   654→    $c->singleton(KeyRegistryInterface::class, function () use ($c) {
   655→        $reg = new KeyRegistry();
   656→        $reg->addKey('app-key-main', $c->get(ConfigInterface::class)->get('app.key'));
   657→        return $reg;
   658→    });
   659→    $c->singleton(EncrypterInterface::class, Encrypter::class);
   660→    $c->singleton(PasswordHasher::class);
   661→    $c->singleton(Hasher::class);
   662→}
   663→```
   664→
   665→- **HUB-04 Identity** — type-hints `PasswordHasher` for `verifyPassword()` and `EncrypterInterface` for at-rest JWT signing-key storage. The Argon2id parameters are pulled from HUB-01 GlobalConfig per ADR-008 (`memory_cost`, `time_cost`, `threads`) and can only ever be *increased* on rehash.
   666→- **HUB-20 Vault** — type-hints `EncrypterInterface` for secret encryption and `KeyRegistryInterface` for envelope-encryption key lifecycle (master KEK → per-secret DEK via `Hasher::deriveKey()`). HUB-20 owns the destruction-after-TTL orchestration that calls `KeyRegistry::deactivateKey()` and later removes the key from the backing store.
   667→- **BRIDGE-01 Vanguard** — type-hints `EncrypterInterface` for payload verification on inbound requests. Per Finding 3, the corrected dependency edge is BRIDGE-01 → CORE-16 (the stale approved `BRIDGE-01.md` wrongly cited CORE-09, the logging primitive; CORE-09 provides no cryptographic operations). BRIDGE-01's "payload verification" obligation is satisfied by calling `Encrypter::decrypt()` on the inbound envelope — if the AEAD tag verifies, the payload is authentic and was encrypted by a holder of the active key; if `CryptoException(TAG_MISMATCH)` is thrown, the payload is rejected as tampered or forged. BRIDGE-01 also uses `Hasher::deriveKey()` for request-HMAC subkey derivation.

   683→## CI Verification Criteria
   684→
   685→- **Branch coverage:** 100% on `Encrypter::encrypt()`, `Encrypter::decrypt()`, `Encrypter::rotateKey()`, `Envelope::jsonSerialize()`, all seven `CryptoException::factory` methods, `KeyRegistry::{getActiveKey,getKey,addKey,deactivateKey,setActiveKey}()`, `PasswordHasher::{hash,verify,needsRehash}()`, `Hasher::deriveKey()`. Tracked via `phpunit/phpunit` coverage with `--coverage-html` artifact uploaded to CI.
   686→- **Static analysis:** `phpstan` level 8 with `bleedingEdge` enabled, zero baseline-ignored errors. `psalm` with `ext-openssl` stubs in `taintAnalysis` mode (catches accidental flow of key material into a sink — e.g. `echo $key` or `error_log($key)`).
   687→- **Known-plaintext round-trip test:** for each of 30 fixture plaintexts (empty string, 1 byte, 1 KB ASCII, 1 KB UTF-8 multibyte, 1 KB binary with NULs, 10 KB, 1 MB random, JSON with nested structures, SQL with quotes, etc.): `encrypt()` then `decrypt()` must return the original byte-for-byte. DataProvider-driven.
   688→- **Tamper detection test:** for each fixture, take the envelope, flip a single bit in the ciphertext (and in a second case, in the tag), and assert `decrypt()` throws `CryptoException` with `errorCode === TAG_MISMATCH`. Also test truncation (drop last byte) and field substitution (replace `ciphertext` with another envelope's `ciphertext`).
   689→- **Key rotation test:** set up a registry with key `A` as active, encrypt payload P₁ (envelope E₁ with `kid=A`), call `rotateKey('B')`, encrypt payload P₂ (envelope E₂ with `kid=B`), decrypt E₁ (must succeed — key A is RETAINED), decrypt E₂ (must succeed), attempt `encrypt($p, 'A')` (must throw `DEACTIVATED_KEY` since A is no longer active).
   690→- **Wrong-key test:** set up a registry with only key `A`. Attempt to decrypt an envelope encrypted under key `B` (constructed by a separate registry). Must throw `CryptoException` with `errorCode === UNKNOWN_KID`. Also: set up two registries each with a different key but the same `kid` value — decrypt with the wrong registry's key must throw `TAG_MISMATCH` (kid resolves, but tag fails to verify).
   691→- **IV uniqueness test:** encrypt the same 1 KB plaintext 10 000 times with the same active key; collect all IVs; assert all 10 000 IVs are distinct (collision probability for 12-byte IVs at 2¹⁰ samples is ~10⁻²⁶, so any collision indicates a broken CSPRNG).
   692→- **Envelope version dispatch test:** construct an envelope with `version = 2` (synthetic) and assert `decrypt()` throws `CryptoException(INVALID_ENVELOPE)` with message containing `unsupported envelope version`. This locks in the forward-compatibility contract: future versions must add a dispatch case before being accepted.
   693→- **Argon2id conformance test:** `PasswordHasher::hash('test')` must produce a string starting with `$argon2id$`; `verify('test', $hash)` must return true; `verify('wrong', $hash)` must return false; `needsRehash($hash)` must return false at default params and true if `memory_cost` is raised.
   694→- **HKDF determinism test:** `Hasher::deriveKey($master, $info, 32)` must return the same output across calls, processes, and PHP versions (HKDF is deterministic); output length must equal `$length`.
   695→- **Key-material taint test:** `psalm --taint-analysis` must report zero taint flows from `KeyRegistry::getKey()` return value to any sink other than the `openssl_encrypt` / `openssl_decrypt` / `hash_hkdf` calls in `Encrypter` and `Hasher`. Specifically, the key must never reach `Psr\Log\LoggerInterface`, `echo`, `print`, `error_log`, `file_put_contents`, or any `__toString` call.

   697→## Security Properties
   698→
   699→1. **AEAD by construction.** AES-256-GCM produces ciphertext that is integrity-protected via the 16-byte authentication tag. `openssl_decrypt` verifies the tag before returning plaintext; on mismatch, it returns `false` and the encrypter throws `CryptoException(TAG_MISMATCH)`. There is no code path that returns plaintext from a tampered envelope — fail-closed is the only behaviour.
   700→2. **IV is cryptographically random and never reused with the same key.** Each `encrypt()` call generates a fresh 12-byte IV via `random_bytes()`. The caller cannot supply an IV — IV generation is the encrypter's responsibility, eliminating the most common GCM footgun (IV reuse exposes the authentication key and breaks confidentiality). With 96-bit IVs and a single key, the NIST SP 800-38D ceiling is 2³² encryptions before collision risk becomes non-negligible; rotation well before that bound is HUB-20's responsibility.
   701→3. **Key rotation is non-disruptive.** `rotateKey()` generates a new key, adds it to the registry, and sets it active; the previous key is RETAINED for decrypt-only operation. Existing envelopes encrypted under the old key continue to decrypt successfully; only new `encrypt()` calls use the new key. There is no migration step, no downtime, and no batch re-encryption requirement.
   702→4. **Keys are never logged.** The `Encrypter` constructor accepts a PSR-3 `LoggerInterface` for operational audit (rotate, mismatch, failure events), but every log call passes only the `kid` and byte-count — never the raw key, plaintext, ciphertext, or tag. `KeyRegistry::__toString()` returns `KeyRegistry(<N> keys, active=<kid>)`, never the key bytes. The CI key-material taint test (above) enforces this statically.
   703→5. **Envelope format is versioned.** Every envelope carries a `v` field (currently `1`). `decrypt()` dispatches on `v` and rejects unknown versions with `CryptoException(INVALID_ENVELOPE)`. This locks in forward compatibility — a future cipher upgrade (e.g. AES-256-GCM-SIV for misuse resistance, or XChaCha20-Poly1305 if a non-AES-NI runtime becomes relevant) can be added as `v=2` without breaking stored v=1 envelopes.
   704→6. **Key length is enforced.** `addKey()` and both encrypt/decrypt paths check `strlen($key) === 32`. A short or long key throws `CryptoException(INVALID_KEY_LENGTH)` and never reaches OpenSSL (which would silently truncate or pad). This eliminates the second most common GCM footgun (192-bit key passed where 256 is expected).
   705→7. **Deactivated keys cannot encrypt.** Once `deactivateKey($kid)` is called, the key remains in the registry for decrypt (envelopes encrypted under it still decrypt), but `getActiveKey()` no longer returns it and an explicit `encrypt($p, $deactivatedKid)` call throws `CryptoException(DEACTIVATED_KEY)`. This prevents an operator from accidentally continuing to encrypt with a compromised key after a rotation event.
   706→8. **Password hashing uses Argon2id, not bcrypt.** Per ADR-008, `PasswordHasher` delegates to `password_hash($plaintext, PASSWORD_ARGON2ID, $options)` with memory-hard parameters (64 MiB, 4 iterations, 2 threads). This makes offline brute-force after a database breach ~100× more expensive than bcrypt at equivalent CPU cost. Legacy bcrypt/PBKDF2 hashes from migrations are accepted on `password_verify()` but immediately upgraded via `password_needs_rehash()` on next login.

   746→**Downstream enablement.** Once CORE-16 lands:
   747→- HUB-04 (Identity) can use `PasswordHasher` for password hashing (replacing any placeholder bcrypt logic) and `Encrypter` for at-rest JWT signing-key storage.

   751→**Rollback.** CORE-16 is additive — it does not modify any existing file in the repository. Rollback is `git rm -r packages/core/crypto/ && composer update`. Downstream impact: HUB-04 password hashing falls back to placeholder logic; HUB-20 secret storage becomes unavailable (Vault service fails to boot); BRIDGE-01 payload verification becomes unavailable (Vanguard rejects all inbound traffic — fail-closed by design). Stateful rollback: existing Argon2id password hashes in the `users` table remain valid (`password_verify()` accepts Argon2id output regardless of whether the `PasswordHasher` wrapper is loaded — it is a thin wrapper around PHP's native function); existing envelopes in HUB-20 storage remain encrypted and unreadable until CORE-16 is restored. There is no data migration on rollback — only the encrypter and hasher become unavailable.
   752→
   753→**Forward compatibility.** The envelope `v` field is the contract surface. Adding a new cipher (e.g. AES-256-GCM-SIV for misuse-resistant IV handling) lands as `v=2`: `decrypt()` grows a `match ($version)` dispatch, `encrypt()` keeps producing `v=1` until an explicit migration is run. This is a SemVer-minor change to CORE-16. Removing a cipher (e.g. deprecating `v=1` after all envelopes are migrated to `v=2`) is a SemVer-major change and requires a deprecation window of at least one LTS release.

   755→## SemVer Impact
   756→**Major** — initial release as `1.0.0`. Establishes the cryptographic baseline of the stack (AES-256-GCM, Argon2id per ADR-008, HKDF-SHA256). The `EncrypterInterface`, `KeyRegistryInterface`, `Envelope`, and `CryptoException` public surface is the SemVer contract; future cipher additions land as minor versions (envelope `v=2` dispatched alongside `v=1`); future cipher removals or interface changes are major. Per ADR-008 §Consequences, Argon2id parameter increases (raising `memory_cost` from 64 MiB to 128 MiB, say) are SemVer-patch — `password_needs_rehash()` upgrades existing hashes transparently on next login, so no breaking change to callers.
